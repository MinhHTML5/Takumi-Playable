## Implementation Quality Assessment

- **Purity contract intact.** The core-purity scan in `test/config.test.js:124-139` still passes: no `phaser` / `document` / `window` reference under `src/core/`. Both `bombQueue` (new) and `bombValueRange` (renamed helper) were introduced without any engine coupling.
- **Snapshot contract intact.** `getState()` returns a frozen root with `bombQueue: Object.freeze([...this.bombQueue])` (simulation.js:373) — non-aliasing per `simulation.test.js:316-326`. The old contract test (`simulation.test.js:409-424`) was extended to require `bombQueue.length === 2`.
- **Generation-time RNG for the queue.** Both the reset seed and the post-drop refill roll through the injected rng at the current elapsed time (`_fillBombQueue`, `dropBomb`). Determinism holds; the "what you see is what drops" contract is asserted by `simulation.test.js:277-294`.
- **Distance spawn is well-behaved.** The while-loop handles multi-trigger frames (spawns one row per trigger with remainder carried); the guard `dy > 0` prevents post-seed spawning under zero rise; the R2 game-over window (30–45 s no-input) still passes across three seeds (`simulation.integration.test.js:152-171`).
- **Bomb queue on drop uses `Array.prototype.shift`.** With a fixed length of 2 this is inconsequential; noted only because it shifts the tail on each drop — not a performance concern at this scale.
- **Sprite-sheet pipeline is fully headless-verifiable.** `buildExplosionSheet` is a pure Buffer producer; the committed PNG is asserted byte-identical to a fresh build (`assets.test.js:117-136`), so drift is detected in CI without a browser.
- **Backward-compatibility with defensive defaults.** `brickValueRange` and `bombValueRange` fall back to legacy config shape when the new keys are absent (difficulty.js:60-66, 90-93); `gameOverTopYOf` defaults to 0. Consistent with the codebase's additive-config posture.

## Issues Found

No blocking issues. Non-blocking observations:

1. **Advisory — bomb visually inside the top bar for its first ~130px of fall.** The bomb is created at `y = 0` (simulation.js:182) — inside the reserved top bar. It is depth-occluded (bomb depth 5, topBarBg depth 30) but the top bar background is 0.92 alpha, so the bomb + label can be faintly visible for the first frames of a drop. Not a functional defect, and not called out by any FR. Deferrable to manual visual tuning.
2. **Advisory — cascading `hit` shake stacks per collision.** When a `greater` bomb chews N bricks in one tick, N `hit`-shake calls hit `cameras.main.shake` in one frame. This is per-spec ("fires on every bomb-hits-brick collision") but may compound visually; the row-clear shake stays independent so this doesn't affect the two-tier read. Deferrable if manual playtest surfaces jitter.
3. **Advisory — taps inside the top-bar band still trigger a drop.** `pointerdown` forwards `worldX` unconditionally (GameScene.js:137-140). FR-8 shrinks the playfield but says nothing about excluding input in the top bar; existing "tap anywhere" behaviour is preserved. Flag only.

None of these justify a remediation loop under `skill:code-review-rubric` (they are advisory, not blocking).
