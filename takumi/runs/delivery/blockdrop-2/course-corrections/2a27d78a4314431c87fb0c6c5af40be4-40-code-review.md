## Code Quality Findings

All findings are advisory. No blockers.

### 1. Advisory — bomb is created at `y = 0`, inside the reserved top bar

- **Where:** `src/core/simulation.js:179-186`.
- **What:** A dropped bomb starts at `y = 0`, but the top-bar band occupies `[0, config.topBar.height = 130]`. The bomb is depth-occluded (bomb depth 5 vs topBarBg depth 30) but the top-bar background alpha is `0.92`, so the bomb + label may be faintly visible for its first ~130 px of fall (~0.14 s at fallSpeed 900).
- **Impact:** Purely visual polish. No functional or invariant violation. Not called out by any FR.
- **Suggested (optional):** Either start the bomb at `y = config.gameOver.topY` so the physical origin matches the shrunk playfield's top edge, or lift the top-bar background alpha to `1.0` to fully occlude. Deferrable to manual visual tuning.

### 2. Advisory — cascading `greater` hits fire N `hit`-shake calls in one tick

- **Where:** `src/scenes/GameScene.js:198-203`.
- **What:** Each `explosion` event of outcome `greater`/`lesser` invokes `cameras.main.shake(...)`. A 4-brick greater cascade in one tick fires four `hit`-shake calls back-to-back within the same frame.
- **Impact:** FR-2 says the hit shake fires on every collision, so this is per-spec. Phaser's shake restarts on repeat calls; the compounded shake may feel jittery on long cascades but the two-tier read vs `rowClear` is preserved.
- **Suggested (optional):** If manual playtest confirms jitter, coalesce per-tick hit shakes (fire once per tick, intensity/duration equal to the strongest queued hit). Not required.

### 3. Advisory — `pointerdown` accepts taps anywhere, including inside the top bar

- **Where:** `src/scenes/GameScene.js:137-140`.
- **What:** `worldX` is forwarded unconditionally; a tap at `pointer.worldY < config.topBar.height` still drops. FR-8 shrinks the playfield but does not explicitly forbid taps in the top bar (existing "tap-anywhere-to-drop" was the pre-course-correction convention too).
- **Impact:** Not a defect vs the spec. Flag only.

### 4. Advisory — commented-out-in-effect legacy config keys

- **Where:** `src/core/config.js:101-104` (`spawn.interval`), `src/core/config.js:158-164` (`difficulty.valueDriftPerLevel`).
- **What:** Both are marked LEGACY in the comment and no longer read by the simulation, but kept because `test/config.test.js:54` and other legacy paths still assert they exist. This is a deliberate additive-config choice.
- **Impact:** No defect. Once test coverage for the pre-FR contract is fully retired, these keys can be dropped along with their asserters. Not scope for this loop.

## Security Considerations

- **Sprite-sheet generator (`scripts/gen-explosion-spritesheet.js`).** Deterministic, no network I/O, no untrusted input, and uses only Node's built-in `zlib`/`fs`. Output path handling accepts absolute or CWD-relative user input; safe for a local build tool. No secrets or credentials touched.
- **Assets committed as binary.** `assets/explosion.png` is 20 644 bytes and asserted byte-identical to the generator's output (`test/assets.test.js:117-136`), so drift or a malicious swap surfaces immediately in CI.
- **No new external dependencies.** `package.json` gained only a `gen:assets` script; the dependency graph is unchanged (Phaser is still vendored, no npm packages).

## Performance Observations

- **Particle-budget bound preserved.** `explosionParticleCount` clamps to `particles.maxConcurrent = 120`. FR-3's increased counts (countGreater 20, countLesser 16, countExact 40) all sit well under the cap. `test/effects.test.js:138-151` asserts the clamp.
- **Texture reuse.** `TEX_SHOCKWAVE` is generated once in `neon.generateShockwave` and reused per burst. Explosion animation is registered once on the global `AnimationManager` (`BootScene.js:39-49`) with an `!exists` idempotency guard.
- **Per-burst sprite churn.** `_playExplosionSprite` allocates one Phaser sprite per collision, torn down on `animationcomplete` — bounded by the drop cooldown (0.5 s) and the animation lifetime (10 frames @ 24 fps = ~417 ms), so at most a handful of overlap under normal play. Acceptable given the cascade cadence.
- **Tween churn on shockwave.** `_spawnShockwave` starts one `tweens.addCounter` per burst. Same bounds as above; no ring pooling needed at this scale.
- **`bombQueue.shift`** — O(2) for a fixed-size queue; not a hot path.
