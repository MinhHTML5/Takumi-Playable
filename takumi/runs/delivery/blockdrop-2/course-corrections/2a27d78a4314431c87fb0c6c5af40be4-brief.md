## Details
## PRD — BlockDrop 2: numeric feedback, juice, and pacing (blockdrop-2)

### Problem
BlockDrop 2 currently expresses brick and bomb values only through color tint. Players can't read the exact numeric value of a brick or the bomb they're about to drop, which forces guessing on whether a drop will clear a row or partially damage it. Related pain points:
- No preview of the next bomb — players can't plan their sequence.
- New brick rows spawn on a fixed 2.5s cadence regardless of rise speed, so they overlap visually and produce untidy stacks.
- Early-game difficulty is flat: bricks are drawn from a mixed [1..30] range from the very first row, not from a small starting range that grows over time.
- Explosion / hit feedback feels lackluster — a single small particle burst per collision, no dedicated hit shake, no shockwave.

### Goals
- Show numeric values directly on brick and bomb sprites.
- Give the player a two-deep bomb queue with visible preview so drops can be planned.
- Reshape the early-game difficulty curve so the game opens easy and ramps up.
- Beef up hit feel with a sprite-sheet explosion animation, more particles, and an expanding shockwave ring.
- Add a light hit-shake distinct from the existing heavier row-clear shake.
- Fix brick spawn cadence so rows stack neatly regardless of rise speed.
- Widen the bomb value range so late-game bombs can decisively cascade (bombs up to 60), decoupled from the brick value cap (which stays at 30).
- Introduce a dedicated top bar for score and the two-bomb preview.

### Non-goals
- No changes to core collision resolution semantics (greater / lesser / exact stay as-is).
- No changes to the seeded RNG contract or headless simulation purity (INV-1, INV-2, INV-3).
- No changes to the game-over screen presentation (Phase 06 GameOverScene stays as-is).
- No new game modes, no scoring rule changes, no persistence.
- No hand-authored art from a designer — the explosion sprite-sheet is script-generated.
- No change to the danger-line pulse behavior itself, only its y position.

### Users
Solo player interacting via single tap / click on a portrait 9:16 canvas.

### Functional requirements

**FR-1 — Numeric labels on bricks and bombs.** Every alive brick sprite shows its current value as a readable numeric label centered on the sprite. The active in-flight bomb shows its current value the same way. Labels update whenever the value changes (a `lesser` hit reduces the brick's remaining value; a `greater` hit reduces the bomb's value as it cascades).

**FR-2 — Two-tier screen shake.** The existing exact-match row-clear shake stays as it is now (heavier: ~220ms, intensity 0.012). A new lighter, shorter shake fires on every bomb-hits-brick collision (both `greater` and `lesser` outcomes). Distinctly weaker than the row-clear shake so players can differentiate them.

**FR-3 — Explosion sprite-sheet + particles + shockwave.** Every bomb-hits-brick collision plays: (a) a ~10-frame sprite-sheet explosion animation, tinted per outcome (value-based tint for greater/lesser; red for exact); (b) more particles than today; (c) an expanding ring that fades over the same lifetime, colored to match the outcome. The sprite-sheet is a monochrome PNG generated at build-time by a Node script, checked into `assets/`, loaded by Phaser via `this.load.spritesheet(...)`, and tinted at runtime.

**FR-4 — Reshaped brick value curve.** Early rows draw from `[1..8]`. The upper cap grows over time up to `30` (the existing brickMax). The lower bound stays at `1` for the whole session. Replaces the current curve where the lower bound drifts up while the upper stays at 30.

**FR-5 — Decoupled bomb value cap.** The bomb value distribution is bounded independently from bricks. Bombs draw from a range that can reach up to `60`. Bricks remain bounded by `brickMax = 30`. Distribution shape (low end, mid-range drift) is left to phase planning; requirements: bombs can exceed the biggest brick, cap is a separate config knob from bricks.

**FR-6 — Distance-triggered brick spawn.** A new brick row is spawned when the most recently spawned row has risen exactly one row-height (120 units) from its spawn position. Replaces the fixed 2.5s spawn interval. Consequences: at higher difficulty (faster rise) rows appear sooner — spawn cadence naturally accelerates with rise speed. Rows always stack neatly. Initial seeded rows are unaffected; the rule takes effect for post-seed spawns.

**FR-7 — Two-bomb queue with preview.** The simulation owns a queue of exactly two upcoming bomb values: `[dropsNext, followingBomb]`. Queue is filled at session start with two freshly rolled bombs. On drop: (1) dequeue front (this is the bomb that flies); (2) roll a new bomb value using current elapsed time; (3) push to tail. Both queued bombs are always visible in the top-bar preview. Preview shows a tinted bomb icon plus the numeric value for each. Leftmost preview = drops on next tap.

**FR-8 — Dedicated top bar.** Reserved band at top of playfield, 120–140 game units tall (tune within that range during planning). Playfield SHRINKS to accommodate: effective top edge for gameplay is `y = topBarHeight`; the danger line moves to `y = topBarHeight`. Layout: score left, two bomb previews right, in queue order (leftmost preview = drops on next tap). Score readout keeps current text style, just repositioned into the bar.

### Constraints
- Language / engine: JavaScript + Phaser (as today). No new frameworks.
- Preserve architectural invariants: INV-1 (`src/core/` engine-free/DOM-free), INV-2 (all randomness through injected seeded RNG), INV-3 (`getState()` read-only snapshot, render never mutates model), INV-5 (one-bomb-per-cooldown drop gate), INV-7 (monotonic value→tint over `[brickMin..brickMax]`).
- `config` shape: new keys additive; existing keys retain meaning unless a FR explicitly reshapes them (e.g. `spawn.interval` becomes unused when FR-6 lands; either kept as legacy or removed — planning decides).
- Explosion sprite-sheet PNG is build-time-generated and committed to the repo; no runtime asset synthesis.
- No performance regression: additional particles + shockwave + sprite-sheet respect the existing `particles.maxConcurrent` budget.

### Assumptions
- Numeric labels use a default readable style (bold monospace with dark stroke for contrast against tint); tunable via config if a specific typography preference emerges.
- Bomb value distribution shape will be tuned during planning to keep the game beatable at the new brick curve.
- Distance-based spawn uses row y-position; edge cases (first post-seed spawn) resolved during planning.
